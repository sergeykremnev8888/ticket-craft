# Notification Service

Внутренний Kafka consumer подтверждённых заказов TicketCraft.
Владеет PostgreSQL `notification_db` и хранит идентификаторы
обработанных событий для дедупликации.

Сервис находится на стадии учебного MVP.
Сейчас уведомление имитируется записью в лог:
отправка email, SMS и push не реализована.

[← Обзор проекта](../README.md)

## Технологии

Java 21, Spring Boot, Spring Kafka, Spring JDBC, PostgreSQL,
Flyway, Jackson 3, Micrometer, Prometheus и OpenTelemetry.

Клиентского бизнес REST API нет. Веб-сервер используется для Actuator.

## Kafka-контракт

| Назначение | Значение по умолчанию |
|---|---|
| Входящий топик | `order-events` |
| Тип события | `OrderEvent` |
| Поддерживаемое состояние заказа | `CONFIRMED` |
| Consumer group | `notification-group` |
| Dead-letter topic | `order-events.DLT` |

Имена топиков настраиваются через `ticketcraft.kafka.topic`.

Событие другого состояния отклоняется с `IllegalArgumentException`.
Ожидается Kafka-сообщение с ключом: listener принимает
`KafkaHeaders.RECEIVED_KEY` как обязательный заголовок.

## Обработка и дедупликация

1. `NotificationConsumer` получает событие.
2. `IdempotentNotificationProcessor` проверяет `messageId`.
3. В одной локальной транзакции выполняются регистрация `messageId`
   в `processed_events` и вызов `NotificationService`.
4. После успешного завершения процессора consumer подтверждает сообщение.

`messageId` должен быть непустым, не состоять только из пробелов
и иметь длину не более 128 символов.

Регистрация выполняется через:

```sql
INSERT INTO processed_events (message_id)
VALUES (?)
ON CONFLICT (message_id) DO NOTHING;
```

Уникальный ключ БД обеспечивает атомарную дедупликацию,
в том числе при конкурентной обработке.

Если `messageId` уже зарегистрирован, повторное событие пропускается.
Содержимое сообщений с одинаковым идентификатором не сравнивается.

Если обработка завершается исключением, транзакция откатывается
вместе с регистрацией идентификатора. Событие можно обработать повторно.

## Retry и DLT

Для обычных повторяемых ошибок по умолчанию предусмотрены
3 попытки обработки: первая попытка и 2 повтора с задержкой 1 с.

`IllegalArgumentException`, включая некорректный `messageId`
и неподдерживаемое состояние заказа, исключён из повторов.

Ошибки JSON-десериализации перехватываются
`ErrorHandlingDeserializer` до вызова бизнес-процессора.

В DLT передаются:

- JSON-событие, если ошибка возникла во время обработки;
- исходные байты, если сообщение не удалось десериализовать.

Сохраняется номер исходной партиции. Поэтому DLT должен иметь
не меньше партиций, чем входящий топик. Конфигурация создания
топиков задаёт им одинаковое число партиций.

Повреждённое сообщение после успешного переноса в DLT
не блокирует последующую обработку партиции.

Публикация в DLT использует `DelegatingByTypeSerializer`:
`byte[]` отправляется без преобразования в JSON,
обычные объекты сериализуются через Jackson 3.

## Гарантии и ограничения доставки

Kafka может доставлять события повторно.
Дедупликация сохраняется в PostgreSQL и переживает перезапуск сервиса.

Локальная транзакция PostgreSQL не является общей транзакцией
с фиксацией Kafka offsets. Повтор после сбоя между коммитом БД
и подтверждением Kafka будет пропущен по сохранённому `messageId`.

Текущая реализация не обеспечивает exactly-once внешнюю доставку:
внешнего провайдера уведомлений пока нет.

Запись в лог также не откатывается вместе с транзакцией БД,
поэтому при сбоях возможны повторные строки логирования.

## Основные настройки

| Параметр | Значение по умолчанию |
|---|---|
| HTTP-порт | `8083` |
| БД | `notification_db` |
| PostgreSQL с хоста | `localhost:5434` |
| Kafka с хоста в профиле local | `localhost:9092` |
| `ticketcraft.kafka.consumer.concurrency` | `1` |
| `ticketcraft.kafka.topic.partitions` | `1` |
| `ticketcraft.kafka.topic.replicas` | `1` |
| `ticketcraft.kafka.retry.max-attempts` | `3` |
| `ticketcraft.kafka.retry.backoff-ms` | `1000` |

Профиль по умолчанию — `local`.
В нём consumer group явно задана как `notification-group`.

Профиль `prod` получает подключения из переменных окружения,
по умолчанию задаёт concurrency, partitions и replicas равными `3`.

Количество реально работающих consumers ограничено числом
доступных партиций.

## Мониторинг

Доступны Actuator endpoint `health`, `info`, `prometheus`,
счётчик обнаруженных дублей и Kafka observations для трассировки.

Адрес OTLP по умолчанию:
`http://localhost:4318/v1/traces`.

## Запуск

Для работы нужны Java 21, PostgreSQL и Kafka.
Для полного сценария TicketCraft нужен Order Service,
публикующий подтверждённые заказы.

Из корня репозитория:

```powershell
.\mvnw.cmd -pl notification-service -am install -DskipTests
.\mvnw.cmd -pl notification-service spring-boot:run
```

Первый вызов устанавливает модуль и необходимые зависимости reactor,
включая `common-dto`, в локальный Maven repository.

## Тесты

```powershell
.\mvnw.cmd -pl notification-service -am test
```

Для интеграционных тестов PostgreSQL нужен работающий Docker.
Kafka-тесты используют Embedded Kafka.

Покрыты дедупликация, конкурентная регистрация события,
откат регистрации при ошибке обработки, валидация messageId,
retry/DLT и продолжение обработки после повреждённого JSON.

## Ограничения и backlog

- Реальная доставка email, SMS и push не реализована.
- Перед подключением внешнего провайдера необходимо определить
  идемпотентность отправки и персистентное хранение задач доставки.
- Отложен отдельный интеграционный тест: событие с некорректным
  messageId направляется в DLT без повторов, не регистрируется
  в processed_events, следующее событие той же партиции обрабатывается.
  Валидация messageId проверена unit-тестами.
- Автоматическая повторная обработка DLT не реализована.
