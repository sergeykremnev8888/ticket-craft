# TicketCraft

**TicketCraft** — это продукт на базе микросервисной экосистемы для бронирования и продажи билетов на мероприятия. 

## Технический стек
* **Базовый фреймворк:** Spring Boot 4.1.1 & Spring Framework 7
* **Платформа:** Java 17+
* **Сборщик проектов:** Apache Maven (Многомодульная архитектура)
* **Базы данных:** PostgreSQL 16 (изолированные СУБД для каждого сервиса)
* **Доступ к данным:** Spring Data JPA (Hibernate) & Spring Data JDBC
* **Брокер сообщений:** Apache Kafka (Confluent Platform)
* **Сериализация данных:** Jackson 3 (`tools.jackson`)

---

## Архитектура и Схема взаимодействия

В системе реализован подход **Database-per-Service** (у каждого микросервиса своя изолированная база данных). Взаимодействие между сервисами разделено на синхронное (чтение каталога) и асинхронное событийное (Event-Driven) через брокер сообщений Kafka.

```text
                  [ Клиент / Frontend ]
                           │
                           ▼ (Синхронный REST HTTP)
               ┌───────────────────────┐
               │    catalog-service    │ ───► БД: PostgreSQL (Порт 5432)
               │   (Каталог и Билеты)  │      Технология: Spring Data JPA / Hibernate
               └───────────────────────┘
                           │
                           ▼ (Асинхронный REST HTTP / Заказ билета)
               ┌───────────────────────┐
               │     order-service     │ ───► БД: PostgreSQL (Порт 5433)
               │  (Оформление Заказов) │      Технология: Spring Data JDBC (Нативный SQL)
               └───────────────────────┘
                           │
                           ▼ (Kafka Producer: Топик "order-events" c ключом userId)
                     ┌───────────┐
                     │   KAFKA   │
                     └───────────┘
                           │
                           ▼ (Kafka Consumer: Чтение потока событий)
               ┌───────────────────────┐
               │  notification-service │ ───► Без базы данных
               │ (Отправка уведомлений)│      Консольное фоновое приложение
               └───────────────────────┘
```

## Структура проекта и Описание модулей

Проект организован в виде многомодульного репозитория (Maven Multi-Module):

*   **`ticket-craft-parent` (Корневой POM):** Управляет версиями всех зависимостей через `dependencyManagement` (`spring-boot-dependencies` и `jackson-bom`). Гарантирует консистентность версий во всей экосистеме.
*   **`common-dto`:** Легковесный Java-модуль (JAR). Содержит общие классы данных и событий (например, `OrderEvent`), которые сериализуются в JSON и передаются через Kafka. Подключается как внутренняя зависимость во все остальные сервисы.
*   **`catalog-service`:** Отвечает за хранение, обновление и вывод пользователю информации о концертах и доступных местах. Настроен на работу с ORM-решением (Hibernate).
*   **`order-service`:** Ядро бизнес-логики. Обрабатывает транзакции создания заказов и резервирования мест. Настроен на работу через чистый JDBC для максимального контроля над SQL-запросами.
*   **`notification-service`:** Фоновый сервис без HTTP-порта. Слушает Kafka, обрабатывает события и симулирует отправку Email/SMS клиентам.

## Важные технические детали и Оптимизации

### 1. Борьба с проблемой N+1 (в `catalog-service`)
Для вывода списка концертов вместе со связанными билетами (`@OneToMany`) по умолчанию Hibernate использует ленивую загрузку (`FetchType.LAZY`), что порождает проблему N+1 запросов в цикле. В проекте это оптимизировано с помощью:
*   Декларативных графов сущностей (**`@EntityGraph`**).
*   Явных запросов слияния (**`JOIN FETCH`**).
*   Это позволяет СУБД выполнять ровно **1 эффективный SQL-запрос** вместо сотен мелких.
*   В целях безопасности пула соединений принудительно отключен опасный паттерн `spring.jpa.open-in-view=false`.

### 2. Защита от двойных продаж / Overbooking (в `order-service`)
При пиковых нагрузках критически важно не продать одно и то же место двум клиентам.
*   Вместо ORM используется **Spring Data JDBC** и сырой SQL.
*   Применяется механизм **Пессимистической блокировки строк** на уровне СУБД PostgreSQL с помощью конструкции `SELECT ... FOR UPDATE`. Строка блокируется до завершения транзакции (`@Transactional`), изолируя параллельные запросы.

### 3. Высокая производительность и Виртуальные потоки (Java 21 / Spring Boot 4)
Проект адаптирован под спецификацию **Virtual Threads**:
*   В конфигурациях включен флаг `spring.threads.virtual.enabled=true`.
*   Встроенный сервер Tomcat обрабатывает каждый входящий запрос не в тяжелом потоке ОС (Platform Thread), а в легковесном виртуальном потоке. Это позволяет системе выдерживать десятки тысяч одновременных соединений при минимальном потреблении RAM.

### 4. Гарантии доставки и Порядок сообщений в Kafka
*   **Сохранение порядка:** События в Kafka отправляются с обязательным указанием **Ключа сообщения (Message Key)**, в качестве которого выступает `userId`. Это гарантирует, что все статусы по конкретному пользователю попадут в одну и ту же партицию Kafka и будут прочитаны строго последовательно.
*   **Идемпотентность:** Так как в сети используется гарантия доставки `At-least-once` (Минимум один раз), `notification-service` спроектирован как **идемпотентный потребитель**. Перед отправкой уведомления ID события сверяется с локальным реестром (кэшем), исключая дублирование писем клиенту при сетевых сбоях брокера.

## Быстрый запуск инфраструктуры

Для локального запуска баз данных и брокера сообщений необходим установленный Docker и Docker Desktop.

1. Перейдите в корень проекта.
2. Запустите Docker-контейнеры в фоновом режиме:
   ```bash
   docker compose up -d
   ```
3. Проверить статус готовности и здоровье контейнеров (Healthchecks):
   ```bash
   docker compose ps
   ```

**Доступные ресурсы на локальной машине:**
*   `postgres-catalog` (БД Каталога): `localhost:5432` (База: `catalog_db`, Логин: `catalog_user`)
*   `postgres-order` (БД Заказов): `localhost:5433` (База: `order_db`, Логин: `order_user`)
*   `kafka` (Брокер сообщений): `localhost:9092`
